# Lab 03 — Observing Background Network Activity During System Updates

---

## Objective

- Understand what network activity occurs when the system performs routine tasks such as updating package repositories
- Learn to observe and interpret short-lived outbound connections using Linux networking tools

---

## Environment

- **Distribution:** Linux
- **Platform:** Terminal
- **User Context:** Standard user with sudo privileges
- **Date:** 2026-03-04

---

## Scenario

Observing background network activity generated by a routine system update. Instead of assuming the system is idle between user actions, the goal is to watch what actually happens at the socket level when `apt update` runs — what connections are opened, what ports are used, and how fast they close.

---

## Technical Concepts Covered

- Baseline network behavior
- Listening sockets vs outbound connections
- System update traffic
- Ephemeral ports
- DNS resolver processes
- TCP connection lifecycle

---

## Commands Used

```bash
ss -tunap
sudo apt update
ss -tunap
ss -uan
watch -n 1 ss -tunap
```

---

## Procedure

1. Ran `ss -tunap` to capture baseline socket state before any activity.
2. Identified all services in `LISTEN` or `UNCONN` state.
3. Executed `sudo apt update` to trigger outbound repository connections.
4. Ran `ss -tunap` immediately after to observe new connections.
5. Used `watch -n 1 ss -tunap` to monitor connection state in real time and confirm how quickly they closed.

---

## Results

**Before the update** — system showed only `LISTEN` and `UNCONN` state sockets:

- Port 53 (DNS) — `systemd-resolved`
- Port 22 (SSH)
- Port 80 (HTTP)

No active outbound connections.

**After `sudo apt update`** — multiple outbound connections appeared:

```
172.29.34.255:41458 → 91.189.92.24:80
172.29.34.255:55570 → 185.125.190.24:443
172.29.34.255:48438 → 34.244.58.147:443
```

All appeared primarily in `TIME-WAIT` state — requests completed before they could be observed as `ESTABLISHED`.

**`watch -n 1 ss -tunap`** confirmed connections were short-lived and disappeared quickly after the update completed.

---

## Evidence

```
# Baseline
ss -tunap
# Port 53, 22, 80 in LISTEN/UNCONN

# During/after apt update
ss -tunap
TIME-WAIT   172.29.34.255:41458  → 91.189.92.24:80
TIME-WAIT   172.29.34.255:55570  → 185.125.190.24:443
TIME-WAIT   172.29.34.255:48438  → 34.244.58.147:443

# DNS resolver identified
systemd-resolved   port 53   UNCONN
```

---

## Key Takeaways

- The system generates real outbound network traffic during routine maintenance — it is never truly idle
- `apt update` contacts multiple external repository servers using ephemeral high-numbered source ports
- `TIME-WAIT` on update connections is expected — requests complete faster than observation
- `systemd-resolved` handles DNS resolution and is visible at port 53 as `UNCONN`
- `watch -n 1` turns a static tool into a live monitor — useful for catching short-lived connections

---

## What This Demonstrates

- Baseline network behavior is observable and predictable once you know what to look for
- Short-lived connections follow the same TCP lifecycle as long ones — they just complete faster
- Understanding normal system activity is the foundation for detecting abnormal activity

---

## Operator Rule

Routine system operations generate short-lived outbound connections. Knowing this baseline is what makes unusual or suspicious network activity recognizable later.

---

## Security / Administration Relevance

- Establishes a network baseline — essential before any security audit
- Helps distinguish expected system traffic from unauthorized outbound connections
- `TIME-WAIT` accumulation during updates is normal; outside of updates it warrants investigation
- DNS traffic from `systemd-resolved` is expected — unexpected DNS processes are not

---

## Time Spent

~30 minutes

---

## Conclusion

This lab confirmed that routine system operations like `apt update` generate measurable, observable network traffic. By watching the socket table before, during, and after the update, the full connection lifecycle became visible — from ephemeral port assignment through `TIME-WAIT` to closure. This is the baseline every administrator needs before they can identify what doesn't belong.
